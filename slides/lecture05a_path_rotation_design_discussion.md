# 第5.5回 固定パス切り換えの設計議論

この資料では、`MTD (Moving Target Defense)` の一部として、`HTTP POST` の送信先パスを切り換えるときに、**サーバ側と Pico 側へ必要な情報をどう与えるべきか** を議論する。

対象は、前資料 [lecture05_mtd_local_post_spec.md](lecture05_mtd_local_post_spec.md) で定めた、ローカル Python 受信サーバと `Raspberry Pi Pico 2 W` の最小構成である。

## 1. 問題設定

固定パス `/ingest` のままでは、攻撃者や観測者から見て送信先が分かりやすい。

そこで、たとえば以下のようにパスを切り換えたい。

- `10:00-10:10` は `/ingest/a`
- `10:10-10:20` は `/ingest/b`
- `10:20-10:30` は `/ingest/c`

このとき難しいのは、**サーバと Pico が同じ切り換え規則を共有していなければ通信できない** ことである。

## 2. 両者が共有すべき情報

最低限、次の情報が必要になる。

- 利用する候補パス一覧
  - 例: `/ingest/a`, `/ingest/b`, `/ingest/c`
- どのタイミングで切り換えるか
  - 時刻ベース
  - 送信回数ベース
  - 乱数や擬似乱数ベース
- どの規則で次のパスを選ぶか
  - 固定順
  - テーブル参照
  - 計算式
- 切り換え開始条件
  - 起動直後から有効か
  - 合図を受けてから有効か
- 旧パスの扱い
  - 即時無効
  - 一定時間だけ併用

## 3. 設計案の候補

## 3.1 案A: ソースコードへ固定で埋め込む

### 概要

- サーバ側にも Pico 側にも同じパス列と切り換え規則を埋め込む
- 例:
  - パス配列 `["/ingest/a", "/ingest/b", "/ingest/c"]`
  - `(seq - 1) % 3` で選ぶ（`seq` は 1 始まり）

### Pico 側に与える情報

- 候補パス一覧
- 選択規則

### サーバ側に与える情報

- 同じ候補パス一覧
- 同じ選択規則

### 長所

- 実装が最も簡単
- 授業で理解しやすい
- ネットワーク以外の依存が増えない

### 短所

- 規則が漏れたらすぐ再現される
- 規則変更のたびに Pico の再書き込みが要る
- 運用としての柔軟性が低い

### 教育向け評価

- `MTD の考え方` を最初に見せるには良い
- `現実の運用` としては弱い

## 3.2 案B: 設定ファイルを事前配布する

### 概要

- 講師が切り換え規則を設定ファイルとして配布する
- サーバはその設定を読む
- Pico はソースコードに同等の設定を転記する

### Pico 側に与える情報

- 候補パス一覧
- 切り換え方式
- 間隔またはタイミング

### サーバ側に与える情報

- 同じ設定ファイル

### 長所

- ルール変更がしやすい
- 仕様書と設定を分けられる
- `設定で動作を変える` という実務感がある

### 短所

- Pico 側は結局書き換えが要る
- 設定の転記ミスが起きやすい
- 授業では運用がやや煩雑

### 教育向け評価

- 中級者には良い
- 初回の授業では少し重い

## 3.3 案C: サーバが次の有効パスを Pico に教える

### 概要

- Pico はまず固定の問い合わせ先へアクセスする
- サーバが「今使うべきパス」を返す
- Pico はその指示に従って本送信する

### 例

1. Pico が `GET /config` を呼ぶ
2. サーバが `{"post_path":"/ingest/b","valid_for_ms":30000}` を返す
3. Pico が `/ingest/b` へ POST する

### Pico 側に与える情報

- 固定の設定取得先
- 返却 JSON の読み方

### サーバ側に与える情報

- 現在有効なパス
- 有効期限

### 長所

- パス変更時に Pico の再書き込みが不要
- サーバ主導で切り換えられる
- 実務的にはかなり自然

### 短所

- `GET /config` という固定目標が残る
- 受講生には少し複雑
- まず設定取得、その後本送信という 2 段階になる

### 教育向け評価

- `制御チャネル` と `データチャネル` の違いを教えられる
- 発展課題として面白い

## 3.4 案D: 時刻ベースで決定する

### 概要

- サーバと Pico が同じ時計と同じ規則を持つ
- 例:
  - 分の下一桁でパスを選ぶ
  - `minute % 3`

### Pico 側に与える情報

- 候補パス一覧
- 時計の基準
- 時刻からパスを決める規則

### サーバ側に与える情報

- 同じ候補パス一覧
- 同じ時刻規則

### 長所

- 追加通信なしで同期できる
- 見た目がスマート

### 短所

- Pico 側の時刻同期が必要
- 授業で時計ずれが起きると詰まりやすい
- ローカル実験ではオーバースペックになりやすい

### 教育向け評価

- 面白いが、初回演習には不向き

## 3.5 案E: 疑似乱数系列を共有する

### 概要

- サーバと Pico が同じ seed を持つ
- 同じ疑似乱数列から次のパスを選ぶ

### Pico 側に与える情報

- 候補パス一覧
- seed
- 乱数アルゴリズム
- 何回目の送信かという状態

### サーバ側に与える情報

- 同じ seed
- 同じ乱数アルゴリズム
- 同じ状態管理

### 長所

- 規則が見えにくい
- `見かけ上の不規則さ` を出しやすい

### 短所

- 状態が 1 回ずれると以後全部ずれる
- デバッグが難しい
- 教育用の最初の題材としては難しい

### 教育向け評価

- 発展テーマとしては良い
- 授業本編には重い

## 4. 比較表

| 案 | 実装難易度 | 授業の分かりやすさ | 再書き込み不要 | MTDらしさ | おすすめ段階 |
|---|---|---|---|---|---|
| A ソース埋め込み | 低い | 高い | 低い | 中 | 初回 |
| B 設定配布 | 中 | 中 | 低い | 中 | 2回目以降 |
| C サーバ指示 | 中 | 中 | 高い | 高い | 発展 |
| D 時刻ベース | 中 | 低い | 高い | 高い | 発展 |
| E 疑似乱数共有 | 高い | 低い | 高い | 高い | 上級 |

## 5. 授業向けに何を採用すべきか

結論として、授業では **2 段階構成** が最も扱いやすい。

### 第1段階

- まずは `案A: ソースコード埋め込み`
- 送信回数 `seq` に応じて
  - 1 回目: `/ingest/a`
  - 2 回目: `/ingest/b`
  - 3 回目: `/ingest/c`
  - 4 回目以降は繰り返し

この段階では、受講生は「固定目標ではなく、複数の候補を回す」という発想を学ぶ。

### 第2段階

- その次に `案C: サーバが次のパスを教える`
- `GET /config` または `POST /config`
- サーバから有効パスと有効期限を返す

この段階では、「制御情報そのものも設計対象である」ことを学ぶ。

## 6. 具体的にサーバへ与えるべき情報

授業用の最小設計では、サーバは以下を持てばよい。

- `allowed_paths`
  - 例: `["/ingest/a", "/ingest/b", "/ingest/c"]`
- `path_mode`
  - 例: `round_robin`, `fixed`, `server_selected`
- `grace_window_seconds`
  - 旧パスを何秒だけ許容するか
- `current_index`
  - 現在有効なパス番号
- `token_map` 任意
  - パスごとの token を持たせるならここで管理する

## 7. 具体的に Pico へ与えるべき情報

授業用の最小設計では、Pico は以下を持てばよい。

- `PATH_LIST`
  - 例: `"/ingest/a", "/ingest/b", "/ingest/c"`
- `PATH_MODE`
  - `round_robin` または `fixed`
- `PATH_ROTATE_EVERY`
  - 何回送信ごとに切り換えるか
- `CONFIG_URL` 発展用
  - 例: `/config`
- `DEVICE_TOKEN` 任意

## 8. 旧パスをどう扱うべきか

教育用には、旧パスを即時に切るよりも、**短い猶予時間を持たせる** ほうが安全である。

理由:

- Wi-Fi の遅延や再送がある
- 受講生ごとに送信タイミングがずれる
- 即時無効だと「概念」より「トラブル」が前に出る

そのため、最初は以下を勧める。

- 新パスを有効化してから `10 秒` は旧パスも受理する

## 9. 推奨する授業向け採用案

最初の教材としては、次の仕様が最も現実的である。

### 採用案

- サーバも Pico も同じ `PATH_LIST` を持つ
- Pico は `(seq - 1) % N` でパスを選ぶ（`seq` は 1 始まり）
- サーバはその全パスを受理する
- 送信 JSON に `mode` と、この段階で新設する `path_index`（選択したパス番号）を含める

### この案の利点

- 実装が簡単
- デバッグしやすい
- 受講生が規則を目で追える
- 次の段階で `server_selected` 方式に移行しやすい

### この案の限界

- 厳密には「サーバが path を教える」設計ではない
- 攻撃者に規則が漏れると追従されやすい

## 10. 発展としての次段階

次に進むなら、以下の順が自然である。

1. `/config` で有効パスを配る
2. パスごとに token を変える
3. パス切り換えと送信周期ランダム化を組み合わせる
4. 旧パス拒否のタイミングを調整する

## 11. 演習で問うべきポイント

- 固定パスから可変パスへ変えると、何が観測しにくくなるか
- Pico とサーバの同期を、どの情報で保つべきか
- 授業では、なぜ時刻同期案より `round_robin` 案が扱いやすいか
- `制御情報を取りに行く固定URL` 自体が新しい固定目標にならないか

## 12. 今回の結論

授業向けの初回実装では、**Pico とサーバの両方に同じ候補パス一覧を持たせ、Pico 側が単純な規則で切り換える方式** が最も適している。

そのうえで、発展課題として **サーバが有効パスを配る方式** を追加するのが、教育的にも実装的にもきれいである。
